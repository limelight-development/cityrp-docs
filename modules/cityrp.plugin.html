Discovery

cityrp.plugin.DiscoverSource ☍

Discovers every plugin under core/plugins, resolving folder and file plugins into one key space. A folder plugin is a folder of sv_init.lua/cl_init.lua/sh_init.lua; a file plugin is a single sv_<key>.lua, cl_<key>.lua or sh_<key>.lua sitting directly in core/plugins. Folders outrank files, and among files sh_ outranks sv_, which outranks cl_. Conflicts and unrecognised Lua files are logged on the server and are never fatal. Every candidate is returned regardless of its own metadata - cityrp.plugin.Resolve reads .meta.lua and decides afterwards.

Returns:

  1. PluginCandidate[] The resolved plugins, ordered by key.

Resolution

cityrp.plugin.ResolveSource ☍

Discovers every plugin, reads its metadata and resolves a deterministic load order. Plugins declare dependencies in an optional .meta.lua beside them; a missing required dependency or a required cycle stops the plugins involved from loading, and is logged rather than raised. A plugin whose metadata declares disabled = true, or whose servers/maps conditions exclude it here, is never added to the discovered set at all - it is absent from the returned order, contributes no sub-resources, and is reported to any dependent as disabled rather than not installed. Everything else discovered is returned even on failure, so a caller can still send a failed plugin's files to the client - only inclusion is gated, on status.

Returns:

  1. PluginEntry[] Every discovered, available plugin, in load order.
cityrp.plugin.SendsSubResourcesToClientSource ☍

Whether any of one plugin's sub-resources will be sent to the client.

The loader AddCSLuaFiles sub-resources after the plugin loop in sh_init.lua has already decided whether to send the plugin's .meta.lua, so a plugin with no cl_init.lua/sh_init.lua of its own can still materialise its folder clientside through them - breathalyser is exactly that shape. Left alone, the client discovers such a plugin with no metadata at all and resolves it with its dependencies and availability conditions never evaluated.

This deliberately mirrors what includeSubResourceFiles and LoadSubResourceItems/Derma actually send rather than merely testing whether the folders exist: sending the sidecar for a plugin that sends nothing else would materialise the folder clientside on its own, which is the opposite failure and the reason the sendsToClient gate exists in the first place.

Parameters:

  • entry PluginCandidate The plugin to test.

Returns:

  1. boolean Whether the client will receive any file from this plugin's sub-resources.

Subresources

cityrp.plugin.LoadSubResourceDermaSource ☍

Includes every derma/*.lua file under one loaded folder plugin, same prefix rules as core/derma: the server sends every file but only includes sh_-prefixed ones, the client includes everything it received.

Parameters:

  • entries PluginEntry[] Plugins in load order, as returned by cityrp.plugin.Resolve.
cityrp.plugin.LoadSubResourceEntitiesSource ☍

Loads the entities/ and weapons/ sub-resources of every loaded folder plugin, in load order. File-based plugins (#2507) never have sub-resources. A plugin that failed to resolve, or a missing entities/weapons folder, is skipped silently.

Parameters:

  • entries PluginEntry[] Plugins in load order, as returned by cityrp.plugin.Resolve.
cityrp.plugin.LoadSubResourceItemsSource ☍

Includes every items/*.lua file under one loaded folder plugin, same convention as core/items: included and AddCSLuaFile'd unconditionally, so item files decide their own realm behaviour. Runs after core/items so plugin items can inherit from bases registered there.

Parameters:

  • entries PluginEntry[] Plugins in load order, as returned by cityrp.plugin.Resolve.
  • log Logger Logger used for debug output.
