Writing Doc Comments

Writing Doc Comments

This site is built by generate.py from two independent sources, so a doc comment lives or dies depending on which one actually reads it:

  1. lua-language-server's --doc JSON export. LuaLS parses the codebase and exports every doc comment it understands — that means real LuaCATS annotations (--- @param, --- @return, --- @class, ...) attached immediately above a declaration, with no blank line in between. A blank line between the comment and the code it describes means LuaLS never associates the two, and the comment is silently dropped from the JSON entirely.
  2. generate.py's own raw-source scan, used only for each file's leading header comment (description, @namespace, etc). This one tolerates a blank line before the code that follows, and accepts either a --[[-- ... --]]-- block or a run of ---/-- line comments.

Everything else in this page is about what each of those two paths actually understands. For the annotations themselves — every tag, its fields, the full type syntax, and the Garry's Mod-specific conventions — see LuaCATS Annotations.

Pipeline

# 1. LuaLS walks the gamemode and exports its own understanding of every doc comment.
lua-language-server --doc=gamemodes/cityrp_2_by_limelightgaming/gamemode \
                     --doc_out_path=src/docs

# 2. generate.py turns that JSON (plus src/docs/topics/*.md) into this site.
python3 src/docs/generate.py --json src/docs/doc.json \
                              --output src/docs/build \
                              --style src/docs/style.css \
                              --topics src/docs/topics

Files under core/server, core/autogen, core/plugins/antihack, core/plugins/screengrab, and every core/items/<category> subfolder are excluded from the export entirely — no doc comment in those paths will ever appear on the site.

Function/variable-level: use real LuaCATS annotations

Write these as --- @tag ... directly above the function/assignment they describe, no blank line. generate.py reads the native args/returns LuaLS already resolved from the function signature itself (so types are accurate even if you never repeat them) and only borrows the tag's text for the human-readable description.

Annotation Syntax Notes
@param --- @param <name[?]> <type[|type...]> [description] Primary way to document a parameter. ? suffix marks it optional.
@return --- @return <type> [<name> [comment]] Primary way to document a return value. One @return line per return value, in order.
@class --- @class [(exact)] <name>[: <parent>...] Defines a struct/type, optionally with inheritance.
@field --- @field [scope] <name[?]> <type> [description] Documents a field of a @class. scope is public/protected/private/package.
@type --- @type <type> Declares the type of a variable, e.g. --- @type string[].
@generic --- @generic <name> [:parent_type] Generic type placeholder for reusable code.
@overload --- @overload fun([param: type...]): [return_type] Documents an additional call signature.
@alias --- @alias <name> <type> Names a type (or enum) for reuse elsewhere.
@enum --- @enum [(key)] <name> Marks a table as an enum, usable at runtime.
@cast --- @cast <value_name> [+|-]<type|?>[, ...] Narrows/widens a variable's type from this point on.
@deprecated --- @deprecated Marks the item outdated (LuaLS strikes it through in editors). This is the LuaCATS spelling — see also the codebase's own @deprecated callout below, which the two share.
@nodiscard --- @nodiscard Warns if the return value is ignored at the call site.
@async --- @async Marks a function as asynchronous.
@see --- @see <symbol> Cross-reference to another documented symbol.
@operator --- @operator <op>[(param_type)]:<return_type> Documents an operator metamethod (__add, etc).
@package / @private / @protected --- @package / --- @private / --- @protected Restricts where the item is considered accessible.
@version --- @version [<|>]<version> Required Lua/LuaJIT version.
@meta --- @meta [name] Marks a whole file as definition-only (not real, executable code).
@as --[[@as <type>]] Inline cast forcing a type onto an expression.
@diagnostic --- @diagnostic <state>:<diagnostic> Suppresses/enables a specific LuaLS diagnostic.

Two annotations are explicitly not used here, even though LuaLS supports them:

  • @module — LuaLS reserves this for its own require()-return-type inference and silently drops any doc comment that uses it. Use the codebase's own @namespace tag instead (see below) — this is the single most common mistake when porting old LDoc comments.
  • @vararg — deprecated by LuaLS itself in favor of --- @param ... <type> [description] for documenting varargs.

Only @param and @return currently have their description folded back into the rendered page by generate.py (by parameter name, and by return position, respectively) — the other annotations above are understood natively by LuaLS/your editor for hover/autocomplete/type-checking, but generate.py doesn't render most of them specially yet.

Minimal example:

--- Gets the value of an env-var.
--- @param name string The env-var to get
--- @return string The value found, nil otherwise
function ENV:Get(name)
	...
end

Function/table-level: this codebase's own tags

These are custom to generate.py, not LuaCATS — but like @param/@return, they're written directly above the function or table they describe, with no blank line, since generate.py only reads the tags attached to that specific declaration's own doc comment:

Tag Purpose
@section <slug> Starts a new named subsection on the module page. Every following item in the file (until the next @section) is grouped under it, so in practice it's usually only written once per group rather than on every function.
@state <word> One of client, server, menu, shared, global, clmenu — drives the realm badge shown next to the item. If a function omits it, it falls back to whatever @state the file's header comment declared.
@warns <text> Renders a "Warnings" callout on that item.
@bugs <text> Renders a "Known Issues" callout on that item.
@deprecated [text] Renders a "Deprecated" callout on that item (falls back to a stock message if no text given).
@internal [text] Renders an "Internal" callout on that item (falls back to a stock message if no text given). 
--- Old warrant lookup, kept for legacy callers.
--- @deprecated Use cityrp.warrants.issue instead.
--- @bugs Does not account for expired warrants.
--- @state server
function cityrp.warrants.legacyLookup(ply)
	...
end

File-header tags: this codebase's own set

The very first comment in a file (block or line-comment style, blank line before the code is fine) is scanned separately for these tags — they are not LuaCATS and LuaLS doesn't know about them:

Tag Purpose
@namespace <name> Not @module. Groups every doc'd item in this file onto one page named <name>, merging with any other file that declares the same namespace (e.g. a cl_*.lua/sv_*.lua pair). Without it, the page falls back to the file's own dotted path (core.libraries.sv_foo). Must not contain ... Only makes sense here — write it once, on the file header.
@state <word> Same word list as the function-level tag above. Written on the file header, this becomes the default realm badge for every item in the file that doesn't declare its own @state.
@copyright, @release, @author Accepted and parsed, but not currently rendered anywhere on the generated site — keep them for humans reading the source, don't rely on them showing up on the page.

The file's own doc comment style can be either form — pick whichever reads better, both parse identically:

--[[-- One-line description.
@copyright 2015-2026 Limelight Gaming
@author Someone
@namespace some.namespace
--]]--

--- One-line description.
--- @copyright 2015-2026 Limelight Gaming
--- @author Someone
--- @namespace some.namespace
