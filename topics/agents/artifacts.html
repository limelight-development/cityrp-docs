    Session artifacts

    What a skill session produces, and where each kind of output must end up. Two rules, split by kind: documents go to a branch and a draft PR, decided work goes to issues. Nothing is left in the transcript.

    master accepts direct pushes for a docs-only change, but documents reach it through a PR anyway: the PR is where the review happens and where the record of what the document was for lives.

    Documents: branch and draft PR

    Any Markdown artifact a skill writes into the repo — an ADR, a design document, research findings, a glossary change — is committed to a branch and raised as a draft PR.

    One PR per session, not per artifact. A session producing two ADRs and a glossary change opens one branch and one draft PR carrying all three.

    Branch naming

    Artifact Path in repo Branch
    ADR docs/adr/NNNN-<slug>.md docs/adr/<slug>
    Design document, or a spec kept as a document docs/design/<topic>/<stage>.md docs/design/<topic>
    Research findings docs/design/<topic>/research-<slug>.md docs/design/<topic>
    CONTEXT.md glossary edits CONTEXT.md docs/context/<slug>

    Where one session produces several kinds, name the branch for the session's topic using the prefix of the dominant artifact.

    One folder per topic. Every document about the same topic lands in that topic's existing folder: successive stages of a design doc, a later redesign, the research that fed it. Coming back to a topic months later means adding a file to docs/design/<topic>/, never creating a docs/design/<topic>-v2/ sibling. The folder is the topic's whole history, in order.

    That includes research: findings live beside the design they feed, as research-<slug>.md in the same topic folder, rather than in a parallel tree of their own. A topic's research and its design are read together, and splitting them by kind means neither half points at the other.

    ADRs are the exception: they stay flat and numbered in docs/adr/, because the number is the ordering and /domain-modeling writes them that way. Several ADRs on one topic are still several flat files.

    These branches deliberately omit the dev/ prefix. AGENTS.md requires dev/ for anything deployable and exempts "doc-topic edits, other .md files, and similar non-code changes" — which is exactly what these are. A docs/ branch tells the deploy pipeline it carries no game code.

    CONTEXT.md is still captured inline

    /domain-modeling writes glossary terms the moment they crystallise, mid-conversation, and that behaviour does not change. What changes is the destination: those edits accumulate in the working tree and go out on the session's artifact branch at the end, with the rest of the session's documents.

    The draft PR

    Open it as soon as the first artifact is committed, so the work is visible while still in progress:

    gh pr create --draft --base master --title "docs: <session topic>" --body-file pr-body.md

    The body says what the session was, what each artifact decides, and links any issue that prompted it. Mark it ready for review when the session ends.

    Delete the branch by hand once merged. Nothing on this repo prunes it for you, and the remote carries the backlog to prove it.

    Exceptions

    • /improve-codebase-architecture writes its HTML report to the OS temp directory by design, so nothing lands in the repo. No branch, no PR.
    • /prototype commits throwaway code to its own throwaway branch and leaves a context pointer on the issue. That branch is a primary source, not an answer — the verdict is captured on the issue and only the validated decision reaches master — so it opens no PR.
    • /implement produces code, not documents. See below.

    Code: /implement

    /implement follows the repo's own branching rules rather than the document rules above, because its output is deployable:

    • Branch dev/<author>/<slug> cut from master. The dev/ prefix is what triggers automatic deploys (AGENTS.md).

    • Conventional Commits on each commit (fix:, feat:, chore:).

    • A draft PR opened once the first commit lands, marked ready when the work is done.

    • public= goes on the PR title only, never on a leaf commit. GitHub squash-merges the title and body into one message, so a public= on a leaf is parsed a second time by the changelog webhook. See commit-message-conventions.md.

    • Before marking the PR ready, run both diff-scoped gates from AGENTS.md. This repo has no typechecker and no test suite, so where the skill says "run typechecking" and "the full test suite", it means these:

      python3 .github/scripts/lint-diff.py --base origin/master gamemodes/cityrp_2_by_limelightgaming
python3 .github/scripts/standards-diff.py --base origin/master

    Specs and decided work: issues

    A finished spec is never left in the conversation. Whatever its size, it is written to GitHub as one or more issues, typed so a later session can pick it up:

    What was decided Issue type Picked up by
    A single implementable piece of work Task /implement
    A body of work spanning several tasks Scheme of Work + sub-issues /to-tickets decomposes it
    An investigation someone must do first Research /research
    A question still needing a decision Discussion /grilling
    A defect confirmed along the way Bug /implement

    Set Priority and Effort per issue-tracker.md. A spec issue is born triaged, so it carries no review-required.

    Capture the sidebar

    Anything raised in passing that is real work but not this session's point — the "oh, we also need to…" — gets its own issue before the session ends, separate from the spec the session is producing.

    • File it with the type that matches what it actually is, and a body that stands alone: someone reading it cold must not need this conversation to understand it.
    • Link it back with a #-reference inside a sentence that carries the reason, never a bare number: "Surfaced while specifying #3401 — same locker loadout path."
    • If it genuinely blocks the main work, wire it with --add-blocked-by rather than describing the dependency in prose.
    • In a /wayfinder session, a sidebar beyond the destination is still filed as its own issue, and the map's Out of scope section links to it. Out of scope means "not on this route", not "not worth doing".
