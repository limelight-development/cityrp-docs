    Networking Library

    cityrp.network (gamemode/core/libraries/sh_network.lua and core/libraries/network/) is the unified replacement for three overlapping systems: engine SetNW*/GetNW*, NSVars, and LocalPlayerVars (core/plugins/networking). See issue #3207 for the full rationale.

    Status: library only. This topic documents the library as it exists today. No call site in the gamemode has been migrated yet — core/plugins/networking is still fully live, and SetNSVar / GetNSVar / SetLPlyVar / SetNW* remain the correct APIs to use until that migration (a later, separate scope) lands. Do not start migrating call sites off this topic alone.

    Why a new library

    • NSVars are player-only. Non-player entities (doors, vehicles, signs) still have no option but the deprecated SetNW*/GetNW* tier — see problems/03.
    • No recipient filtering. NSVars are net.Broadcast() or nothing; LocalPlayerVars are owner-only or nothing. Nothing in between — no faction-private, gang-private, or police-private state without hand-rolling a new net.* message.
    • The registration ID is a positional wire contract. NSVars assign IDs by call order (#registered + 1); any load-order divergence between the client and server realm shifts every ID and silently corrupts every value, with no error.
    • Recycled indices leak state. The client keys NSVar state by raw entity index (PLUGIN.NSVars[entIndex]) and never clears an entry on disconnect, so a new player who receives a recycled index inherits whatever the previous occupant left behind.
    • Broadcast while out of PVS is lost. There is no pull-on-visible path — a value set while a client is out of range never reaches it unless something else happens to resend it later.

    Core concepts

    A network var is registered once, in shared code, with a builder chain:

    cityrp.network.Register("cityrp_VehicleLocked")
	:SetEntity()
	:Bool()
	:SendPVS()
	:SetHook("CityRP.VehicleLockChanged")
	:Accessor("VehicleLocked")

    Registration must happen before the registry seals, which occurs automatically on the Initialize hook (both realms). Registering afterward is a logged error and the var is never networked — register vars at file scope or from an early hook, not lazily on first use.

    Scope

    Exactly one scope per var, set with one of these (default: :SetEntity()):

    Method Storage Default recipients
    :SetEntity() On the entity (ent.__netvars) Broadcast
    :SetPlayer() Same as Entity — a player is an entity. Routes :Accessor() to FindMetaTable("Player") — see Accessor targets below. Broadcast
    :SetVehicle() Same as Entity. Routes :Accessor() to FindMetaTable("Vehicle"). Broadcast
    :SetWeapon() Same as Entity. Routes :Accessor() to FindMetaTable("Weapon"). Broadcast
    :SetLocalPlayer() On the owning player That player only, always — recipient methods below don't apply
    :SetGlobal() In the library, no owning entity Broadcast

    :SetEntity(), :SetPlayer(), :SetVehicle(), and :SetWeapon() are identical in storage and wire framing — cityrp.network.IsEntityScope(scope) is true for all four. The only thing that differs between them is which metatable :Accessor() attaches its generated methods to. :SetLocalPlayer() also routes to FindMetaTable("Player"), despite differing in storage/recipients from the other four.

    Codecs

    Call one codec method per var (default is :Auto() if none is called):

    Method Wire shape
    :Bool() 1 byte via net.WriteBool
    :Bit() Raw bit via net.WriteBit/net.ReadBit, returns 0/1 rather than a boolean
    :Nibble() / :UNibble() 4-bit signed/unsigned
    :Byte() / :UByte() 8-bit signed/unsigned
    :Short() / :UShort() 16-bit signed/unsigned
    :Int() / :UInt() 32-bit signed/unsigned
    :Integer(bits) / :UInteger(bits) Explicit 1-32 bit width
    :Float() 32-bit IEEE float
    :Double() 64-bit IEEE double
    :Long() Alias of :Double() — see Integer widths below
    :String() net.WriteString
    :Vector() Three signed components, each auto-choosing float vs. compact integer
    :Normal() Compact vector encoding for components that stay within ±1
    :Angle() Same per-component encoding as :Vector()
    :Color() RGB plus an optional alpha byte (only sent if alpha isn't 255)
    :Entity() net.WriteEntity/net.ReadEntity
    :Player() net.WritePlayer/net.ReadPlayer — narrower than :Entity(), sized off MAX_PLAYER_BITS instead of MAX_EDICT_BITS. :Auto() picks this over :Entity() on its own whenever the value is a player.
    :Table() Recursive, self-describing — each key/value goes through :Auto()
    :Data(maxLen) Fixed-length byte string via net.WriteData/net.ReadData
    :Auto() Self-describing: a small type tag, then the value. What NSVars do today.
    :Write(fn, opt) / :Read(fn, opt) Custom codec — see Custom codecs below
    :Enum(list) Fixed set of legal values — see Enums below

    Integer widths

    net.WriteInt/net.WriteUInt only accept 1-32 bits. NSVars' NETTYPE_LONG (64) and NETTYPE_XLONG (128) passed 64/128 to those functions and could never actually work. Separately, GLua numbers are IEEE doubles, so no integer above 2^53 can round-trip through Lua regardless of how it's framed on the wire. :Long() is therefore an alias of :Double() — the widest integer GLua can actually represent exactly — not a wider integer codec. There is no :XLong(); nothing in Lua can hold the value, so the name would only reproduce the old illusion.

    Custom codecs

    :Write(fn, opt) / :Read(fn, opt) bypass the built-in codec table entirely. Because the manifest (below) can't describe an arbitrary function, a custom-codec var is always sent alone in its own message, never batched alongside other vars — an undecodable custom value can then only ever corrupt its own message, not a whole batch riding with it. Both realms must register the same var with matching :Write/:Read calls; a client that never called :Read() for a name the manifest describes as Custom-coded logs an error and drops that message when one arrives.

    Enums

    :Enum(list) declares a var's legal values as list, a sequential (ipairs-ordered) array, and picks between two wire strategies by comparing their actual bit cost:

    • Direct value (batchable) — if list is entirely integers, the value itself goes on the wire, sized to its min/max via :Integer/:UInteger (signed only if the set dips below zero). No offset from the minimum is applied even when every value shares a large common magnitude (e.g. {100, 101}) — an offset would itself need a per-var :Write()/:Read() closure, i.e. CODEC_CUSTOM, which is exactly the cost this path exists to avoid. Order carries no wire meaning here.
    • Mapped index (not batchable) — the value's index in list goes on the wire instead, via an auto-generated :Write()/:Read() pair sized to #list. CODEC_CUSTOM under the hood (see Custom codecs above), so a resync entry using it never shares a message with sibling vars on the same entity — its own WriteIndexHeader plus framing, and its own resync-queue slot. Order does matter here: it's the wire index, so both realms must register the same var with the same list in the same order.

    For an all-integer list, the mapped index is only chosen if it beats the direct-value bit cost by more than cityrp.network.RESYNC_GROUP_OVERHEAD_BITS (24), the approximate resync-framing cost of escaping batching. A list containing anything non-integer (strings, mixed types) always uses the mapped index; there's no numeric value to size a direct encoding from.

    Either way, Setting a value that isn't in list is rejected — logged and dropped, never stored or sent — rather than silently encoding as something adjacent or vanishing into no enum value at all. nil (clearing the var) always bypasses this check.

    -- Direct value: dense, low-magnitude set — 3 bits, batchable.
cityrp.network.Register("cityrp_Rank"):SetPlayer():Enum({1, 2, 3, 4}):Accessor("Rank")

-- Mapped index: small set, but string-valued (no direct encoding available) — 3 bits, not batchable.
cityrp.network.Register("pass"):Enum({"grey", "green", "blue", "orange", "red"}):Accessor("Pass")

    Recipients

    Only meaningful for Entity/Player/Vehicle/Weapon/Global scope — LocalPlayer scope is always owner-only regardless.

    Method Behaviour
    :Broadcast() Default. Sends to everyone.
    :SendPVS() net.SendPVS(ent:GetPos()) — everyone who can potentially see the position.
    :SendPAS() net.SendPAS(ent:GetPos()) — everyone who can potentially hear it.
    :SendOmit(fn) fn(ent, value) returns who to exclude; everyone else gets it.
    :Filter(fn) fn(ent, value) returns who receives it — a Player, a Player[], or a CRecipientFilter.

    :Filter() is the only secrecy boundary. PVS, PAS, and Omit are treated as bandwidth optimizations, not authorization: resync and the join bootstrap (below) always include a PVS/PAS/Omit var's current value for a player who's asking, because pull-on-visible only fires once the client is already in a position to receive it anyway. If a value must never reach a player at all — faction, gang, or police-private data — use :Filter(), not :SendOmit(). :Filter()'s callback doubles as that authorization check: the same function that decides who gets a live update also decides who's allowed to pull it via resync, so there's exactly one predicate to keep correct, not two that can drift apart. Keep :Filter() callbacks cheap and free of side effects — they can run once per set and again per resync candidate.

    Behaviour

    Method Effect
    :SetHook(name) Runs hook.Run(name, ent, newValue, oldValue, predicted) on both realms when the value changes. predicted is true only for a :Predictable() var's client-side local apply — see below.
    :AutoHook() Shorthand for :SetHook("CityRP.Network.<name>.Changed") — use when you don't care what the hook is called.
    :Accessor(name) Generates Get<Name>() (both realms) and Set<Name>() (server only, unless :Predictable()) — see Accessor targets below for which metatable.
    :Predictable() Also generates a client-side Set<Name>() for local prediction — see below. Only valid on :SetLocalPlayer().
    :SetNoSync() Excludes the var from the join bootstrap and resync — push-only. A client that was out of PVS during a push never gets it.
    :SetDefault(value) What Entity:GetNetVar/cityrp.network.GetGlobal return before anything is set.

    Client-side prediction

    :Set<Name>() is normally server-only — setting is server-authoritative, and the underlying SetNetVar/SetGlobal don't exist on the client realm at all (sv_send.lua is a server-only file). :Predictable() opts a :SetLocalPlayer() var out of that: the client gets its own Set<Name>() too, which applies the value locally (storage + the :SetHook() hook, with predicted = true — never a network send, the client has no authority to send anything) instead of calling into the server-only machinery.

    This is for the standard prediction-and-reconciliation shape: client-side code that runs under IsFirstTimePredicted() calls Set<Name>() immediately for instant feedback, while the server keeps computing and pushing the authoritative value exactly as it always did. When that confirmed value arrives back at the client through the normal decode path, it overwrites whatever was predicted locally — correcting any drift the same way it always corrected a live update, no special-case reconciliation code needed. If the client's prediction already matched, the delta guard in ApplyValue means nothing observable happens; if it didn't, the value snaps to the server's.

    Only valid for :SetLocalPlayer() — a client predicting some other entity's state has no server-authoritative copy of that entity's future value to reconcile against, so the scope doesn't make sense there. Using :Predictable() on any other scope logs an error at accessor-generation time and simply doesn't generate the client-side setter, rather than producing a footgun that looks like it works.

    cityrp.network.Register("_Stamina"):SetLocalPlayer():UByte():Accessor("Stamina"):Predictable()

-- In shared code, guarded the same way any other predicted mutation is:
if SERVER or IsFirstTimePredicted() then
	ply:SetStamina(newValue) -- works on both realms now
end

    Accessor targets

    :Accessor(name) attaches to FindMetaTable("Entity") for Entity/Global scope, FindMetaTable("Player") for Player/LocalPlayer scope, and FindMetaTable("Vehicle")/FindMetaTable("Weapon") for those. Calling Entity:GetNetVar/SetNetVar itself would already work identically regardless — GMod resolves a method not found on a more specific metatable by falling through to Entity's — but the one case that fallthrough doesn't cover is a same-named method the more specific metatable already defines natively: it would shadow an Entity-attached Get<Name>/Set<Name> for every entity of that type, silently calling the native method instead of yours. Attaching directly to the matching metatable instead puts your accessor closer than Entity's in the lookup chain, so it wins.

    This is a real, present-day risk, not a hypothetical one: sv_vehicle.lua's locked, engine_on, and HP state — the values modern-apis.md names as the reason vehicles still use the otherwise-avoided SetNW* tier — are exactly the kind of vehicle-specific accessor a scope 2 migration would want to name Locked/EngineOn/HP, and FindMetaTable("Vehicle") is already extended in this codebase (core/metatables/sh_vehicle.lua).

    Reading and writing

    -- Server only
ent:SetNetVar("cityrp_VehicleLocked", true)
cityrp.network.SetGlobal("WeatherState", 2)

-- Both realms
local locked = ent:GetNetVar("cityrp_VehicleLocked", false)
local weather = cityrp.network.GetGlobal("WeatherState", 0)

-- Server only; runs fn(ply) once ply's handshake completes, or immediately if it already has
cityrp.network.WaitForPlayer(ply, function(ply)
	ply:SetNetVar("cityrp_Job", "Citizen")
end)

    Entity:SetNetVar/SetGlobal on an unregistered name, the wrong scope's accessor (e.g. Entity:SetNetVar for a Global-scoped var), or :SetNetVar for a LocalPlayer-scoped var on a non-player entity are all logged errors, not silent no-ops or thrown exceptions.

    Wire protocol

    Three net strings, two used in both directions:

    Message cl → sv sv → cl
    cityrp.network.Sync Client's net channel is ready The manifest, then the join bootstrap
    cityrp.network.Resync Batched entity indices to resync Batched per-entity/global var groups
    cityrp.network.Update — A single live var change

    The manifest is what fixes the positional-wire-contract bug. The server seals the registry (sorted var names → sequential IDs) and sends every client id → name, scope, codec, arg, with the ID bit-width itself in the header. The client never assigns its own IDs — it waits for this message and matches entries by name. A load-order difference between realms can no longer desync anything: at worst, a var one realm doesn't have registered locally gets a synthetic entry built straight from the manifest, logged once, and keeps working via GetNetVar/SetNetVar.

    A joining player's Sync announce is retried every 2 seconds (up to 5 attempts) until the manifest arrives. The server does not send Update/Resync traffic to a player until their handshake completes — an update sent before the manifest would be undecodable, and because sets are delta-guarded, that value would then be lost for good.

    Storage and the recycled-index bug

    Entity/Player-scoped values live directly on the entity's own Lua table (ent.__netvars), the same way Photon SimpleNet stores state, on both realms. This is what retires NSVars' recycled-index bug: GMod hands a freshly-created entity a new Lua table regardless of which index it reuses, so there is nothing left over to clean up and nothing that can leak between occupants of the same index.

    Resync

    Modeled on Photon SimpleNet's pull-on-visible design:

    1. Client requests a resync when an entity is created over the network (GM:NetworkEntityCreated) or re-enters this client's PVS (GM:NotifyShouldTransmit). Requests debounce to at most one batched message per frame.

    2. Server queues the requested entities per player and drains the queues from Think, subject to two ConVars:

      ConVar Default Meaning
      cityrp_network_resync_rate 32 Entities resynced per frame, server-wide.
      cityrp_network_resync_rate_player 8 Max entities resynced per frame for any one player.

      Draining is round-robin across players with a persistent cursor, so a player with a large queue cannot starve everyone else — every player with a non-empty queue gets served within a bounded number of frames regardless of how full anyone else's queue is.

    3. Each player's queue is a weak-keyed set of entities ({[Entity] = true}, __mode = "k"), not an ordered array. Both a disconnecting player's whole queue and an individual removed entity clean themselves out of every queue automatically; PlayerDisconnected/EntityRemoved hooks additionally purge eagerly rather than waiting on the next GC pass.

    4. The join bootstrap reuses this same path: on handshake, every currently-known networked entity is queued for the new player exactly as if it had just re-entered their PVS, so a join gets the same per-frame rate limiting as any other resync rather than a separate bulk-send path to reason about. Global values and the joining player's own LocalPlayer-scoped values — neither tied to any entity's visibility — are sent once, directly, alongside the manifest.

    cityrp_network_sync_bytes (default 8192) is the flush threshold, in bytes, for a batched Resync message — checked between entity groups, so a message can exceed it by up to one group's worth of vars. That default leaves roughly 57 KB of headroom under the 65536-byte net message cap.

    Diagnostics

    cityrp_network_dump — server console/RCON only (same guard as cityrp_log_set). Prints the sealed registry (id, name, scope, codec) and, per connected player, handshake status and resync queue depth. Verbose per-message logging goes through the existing logging library, not a dedicated ConVar:

    cityrp_log_set network DEBUG
